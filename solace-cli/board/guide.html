Using Solace

Solace lets AI coding agents build and change your project while you direct the work. You describe tasks on this board, choose which model works on each one, answer the agents' questions, and approve or reject what they did. The agents do all their work through Solace, which checks and records every change they make.

How it works

Your project's code is kept in a store inside the project, in the .solace/ folder, where each function, type and constant is a separate entry. The source files on disk are written from that store. Agents never edit files directly. They read and change code one entry at a time through Solace, and every change is type-checked before it is kept.

Agents have no shell and no general file access. They get one tool, Solace, plus web access for looking things up. That means:

  • every change an agent makes goes through Solace's checks, and can be undone;
  • an agent can't delete files, run arbitrary programs or change Solace's own settings;
  • anything an agent needs that Solace doesn't offer, it has to ask you for.

The drawbacks: an agent is limited to what Solace provides, so some tasks that are easy with a shell (a quick throwaway script, for example) need a command you declare for it. And you shouldn't edit the source files by hand either, because Solace rewrites them from its store.

Tasks

A task is a piece of work you write for an agent: a title and a description. The description can refer to existing behavior, ask for changes, suggest something new, or just ask a question.

Each column says what an agent may do there. In Planning, investigate starts an agent that looks into the task and reports back: an answer to a question, or a plan for the change. It changes nothing. If the task was only a question, complete it once you have the answer. Otherwise assign it, and the agent that does the work gets the report with the task's other notes. An agent changes the project only once the task is Assigned. A review agent, in Needs review or Blocked, looks at what the task changed and gives feedback.

The default columns

ColumnWhat it meansWhat you can do
BacklogWritten, not yet being plannedPlan it, or cancel it
PlanningYou're shaping the taskAsk an agent to investigate it, assign it to a model, complete it (when it only needed an answer), send it back, or cancel it
AssignedAn agent is workingStart a new agent on it, or cancel it
BlockedThe agent needs an answer, or couldn't continueAnswer and unblock it, start a new agent, ask for a review, or cancel it
Needs reviewThe agent says it's finishedApprove it, then complete it; ask for an agent review; reassign it for fixes; start over; or cancel it
Done, CancelledFinished either wayNothing

A task with an agent on it says so on its card: Agent investigating, Agent working, Agent reviewing, Waiting for your answer or Agent paused.

If a review finds problems, enter any additional instructions in Note / answer / instructions and choose reassign. The task returns to Assigned and a work agent gets the review feedback and notes. Existing changes are kept, and any approval is cleared. You can select another model first. Wait for an active review to finish before reassigning. Start over instead undoes the task's changes before starting another agent.

You can pause any task that isn't finished, and resume it later. A paused agent stops at its next step and keeps what it knows.

A task can't be completed until you approve it. If you move an approved task anywhere else, for example by starting over, it loses the approval.

Cancel and Complete ask for confirmation. Cancel stops the task's agents and reverts its changes. Complete keeps the changes and closes the task, removing its undo records; the board cannot reopen or revert it afterwards. Dismissing either dialog leaves the task and your entered instructions unchanged.

You can change the columns and what's allowed in each in the project's solace.toml (see Settings below).

Questions and attention

Solace keeps the author's conversation through investigation, implementation and review fixes when compatible. Each review starts fresh. Changing models or losing a conversation automatically gives the next agent a handoff with feedback, changes and verification results. You do not need to manage sessions. Finishing agents get time to exit normally; author conversations are cleaned up when the task is completed or cancelled, and reviewer conversations after their review.

When an agent needs a decision, it asks a question with a few options, and the task moves to Blocked. The agent waits, keeping everything it has learned so far. Pick an option or submit a written answer. Once every pending question is answered, the same agent automatically carries on. An investigating agent stays in Planning and continues the same way. If you paused the task, answers are saved and it stays paused until you choose resume. If you'd rather start fresh, new agent starts another one, which gets the task's notes and your answers.

A task marked Needs attention is waiting on you. That happens when an agent asks a question, when an agent stops unexpectedly (it crashed, ran out of time, lost its connection, or its model became unavailable), or when Solace was restarted while an agent was working. The reason is shown on the task, together with the agent's last message when there is one. The run's activity shows everything that led up to it. The mark goes away when you next act on the task. To continue, unblock it or start a new agent, and choose a different model if the first one isn't working.

Following an agent

Every run of an agent is listed under Runs on the task, newest first. Follow live shows what the agent is doing as it happens: its messages, its thinking, and each Solace command it runs. Open a command to see what it sent and what came back; a ✗ marks a command that failed. Show activity does the same for a run that has ended. It's a view only, so you can't interrupt or talk to the agent from it. Use a note, an answer or pause for that.

Undoing a task

Cancel and start over undo everything the task changed, bringing the code and resource files back to how they were before it started. Solace refuses to undo a task when that would affect another open task: if a later task changed the same code, or depends on something this task added. The refusal names the other task, so you can undo that one first or leave things as they are.

Solace doesn't keep a history beyond that. Use your own version control (such as git) for history.

Models

You choose a model each time you assign a task or start a new agent. Solace runs the model through an agent program you already have installed and signed in to: the Codex CLI for OpenAI models, or Claude Code for Claude models. Solace doesn't store any credentials itself.

A list of current major models is built in. A model that can't be started right now is greyed out in the list, with the reason: the agent program isn't installed, it isn't signed in, or a key it needs isn't set.

Add your own models, or change the built-in ones, in ~/.config/solace/config.toml:

task_timeout = 3600            # seconds an agent may work; time spent waiting for you doesn't count

[[models]]                     # a model through the normal Codex sign-in
id = "codex-terra-high"
label = "Codex · Terra (high effort)"
agent = "codex"
model = "gpt-5.6-terra"
effort = "high"

[[models]]                     # any OpenAI-compatible endpoint, through Codex
id = "local-qwen"
label = "Qwen3 Coder (local)"
agent = "codex"
model = "qwen3-coder"
endpoint = { kind = "openai", base_url = "http://localhost:11434/v1", key_env = "LOCAL_LLM_KEY" }

[[models]]                     # any Claude-compatible endpoint, through Claude Code
id = "proxy-sonnet"
label = "Sonnet via our proxy"
agent = "claude"
model = "claude-sonnet-5-5"
endpoint = { kind = "anthropic", base_url = "https://llm-proxy.example.com", key_env = "PROXY_KEY" }
  • An entry with the same id as a built-in model replaces it. Add presets = false at the top to hide the built-in list.
  • An endpoint's key is never written in the file. key_env names an environment variable that holds it, and Solace reads that variable when it starts the agent. Leave key_env out for an endpoint that needs no key.
  • Codex talks to OpenAI-compatible endpoints through the Responses API, so the endpoint has to support it.

Contract view

When a task changes the project, its detail panel shows a review summary and a link to the contract view. The graph reports entry points, logic, derived effects, tests and project files. Effects are inferred from known calls and external declarations; they are not guarantees. Review compares the current project with its state before the task, and you can run the task's tests from the view API. Open Contract view to explore the drawing sheet. Search by name or summary, select a box to expand its connections and read its detail, or open Files for each file’s tier. Overview fits the whole drawing; disconnected entries fill rows. The title block identifies the project and store version. A note says when no effects were found. On a phone, open Legend for kind colours and connector meanings. Drag the sheet or use the zoom buttons; keyboard users can focus a box and press Enter. A task’s review link marks additions, changes and removals and runs its tests when needed. Use Show source only when you want the source text. Run forms and replay come later.

File tiers in the graph describe how Solace treats each file. Tier 2 is the managed manifest. Tier 3 resources can be changed by agents and are restored when a task is undone. Tier 4 files are outside Solace's tracked resources. Project settings are for the human to change.

What agents can touch

Every file in the project is in one of these groups:

GroupFilesWhat agents can do
SourceGleam files in src/ and test/Read and change code through Solace, one entry at a time
Manifestgleam.tomlRead and write
ResourcesFiles you list under resources in solace.tomlRead and write, checked by any validator you declare
IgnoredEverything else: build output, logs, anything .gitignore ignoresRead and write; excluded from symbol searches
Solace's own.solace/ and solace.tomlNothing, except reading solace.toml

Resource patterns classify files; they do not grant write access. Agents can also update ignored files such as README.md or create bin/coolcalc without changing the patterns. File writes are limited to 256 KiB unless you change the limit, and require a current read or an exact replacement. Resource and ignored file contents never appear in symbol searches.

Settings

solace.toml in the project's root holds the project's settings. Import creates a starter file if it is missing and preserves an existing one. Only you edit it; agents can read it, and an agent that needs a change has to ask you. Every part is optional.

resource_limit = 262144                    # bytes
resources = ["priv/**/*.html", "docs/**/*.md"]
ignore    = ["priv/generated/"]

[validators]                               # must pass before a resource change is kept
"priv/**/*.html" = ["tidy", "-q", "-e", "{file}"]

[commands]                                 # extra commands agents may run
smoke = { run = ["gleam", "run", "-m", "smoke"], timeout = 60 }

Agents can always check, test, format and build the project. Under [commands] you add anything else they may run. Commands run without a shell, so agents can't chain or alter them, and they can pass extra arguments only to a command that sets args = true.

A [board] section replaces the default columns and actions. It's described in the Solace repository's board specification.

Limits for now

  • Projects must be written in Gleam.
  • One agent works on a project at a time. While one is working, assigning another task is refused.
  • Tasks that are still open aren't kept apart: a later task sees the unapproved changes of earlier ones.
  • The board runs on your machine only, for one person, with no sign-in.
