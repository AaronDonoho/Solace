Using Solace

Solace lets AI coding agents build and change your project while you direct the work. You describe tasks on this board, choose which model works on each one, answer the agents' questions, and approve or reject what they did. The agents do all their work through Solace, which checks and records every change they make.

The menu bar

A menu bar at the top of every page has three pages: Board (/), Migration (/migrate) and Contracts (/contracts, or /p/<folder>/contracts for one project in a workspace). This guide is a separate page.

How it works

Your project's code is kept in a store inside the project, in the .solace/ folder, where each function, type and constant is a separate entry. The source files on disk are written from that store. Agents never edit files directly. They read and change code one entry at a time through Solace, and every change is type-checked before it is kept.

Agents have no shell and no general file access. They get one tool, Solace, plus web access for looking things up. That means:

  • every change an agent makes goes through Solace's checks, and can be undone;
  • an agent can't delete files, run arbitrary programs or change Solace's own settings;
  • anything an agent needs that Solace doesn't offer, it has to ask you for.

The drawbacks: an agent is limited to what Solace provides, so some tasks that are easy with a shell (a quick throwaway script, for example) need a command you declare for it. And you shouldn't edit the source files by hand either, because Solace rewrites them from its store.

Migrating an existing project

To start using Solace on a Gleam project you already have, run solace serve in its folder, open Migration in the menu bar (/migrate) and choose Migrate this project. The page stops polling for status when you leave it. Solace makes a copy of the whole folder next to it, called solace-migration, and sets up the copy to use Solace. Your folder isn't changed. You can try Solace in the copy for as long as you like, then switch to it or delete it.

When you start, choose which Gleam projects to set up. You can also give commands that check your app works, one per line, such as a script that starts the app and requests a page. Solace runs each one in your folder before migrating and in the copy afterwards, and compares the results. Without any, only builds and tests are compared.

The copy has exactly the same code as your original, errors included. If a build or a test fails before migrating, it fails in the copy too. That doesn't stop you from switching: fixing it is ordinary work afterwards.

Keeping your original folder safe

  • Before running anything, Solace looks in the copy for anything that could change your original folder from there, such as a script that uses the folder's full path. If it finds something, it stops and lists it. Look at each one, then choose Continue.
  • A link that points into your original folder is changed to point at the same place in the copy.
  • If bubblewrap (bwrap) is installed, your original folder is read-only to every command Solace runs, including agents' commands while you work in the copy. Without it, the report says so.
  • If the migration stops partway, the copy is kept so you can see what happened. Delete the copy removes it.

What Solace checked

Once the copy is ready, the board shows it, with both folders' paths, and lists what Solace checked. ✓ means fine, ✗ a problem to fix before switching, and ! something worth a look. Choose Show details on a line to see the differences or a command's output.

  • Copying your folder: everything was copied, and which projects were set up.
  • Your code, written back by Solace: Solace keeps your code in its own store and writes the files from it. Each file should come out exactly the same, or differ only in blank lines and spacing between definitions. This is compared once, when the copy is made, so changes you make in the copy later don't count against it.
  • Builds and tests: each project builds and passes the same tests as before, and your check commands give the same results.
  • Anything that could reach your original folder: files, links and settings in the copy that point outside it.
  • Your original folder: nothing in it has changed since the copy was made.
  • Your code without Solace: with Solace's files removed, your code still builds and passes its tests, so you can stop using Solace at any time.

The buttons

  • Run the checks again builds and tests the copy again and compares it with your original folder. Do this after changing the copy.
  • Switch to the copy moves your original folder to <name>.pre-solace and puts the copy in its place, then builds and tests it there. If that fails, both folders go back. It's available once nothing is marked ✗. If you changed your original folder after the copy was made, Solace won't switch, since you'd lose those changes, and lists what changed.
  • Delete the copy deletes the copy and anything done in it. Your original folder stays as it is.
  • Switch back, after switching, puts your old folder back and moves the Solace version to solace-migration, with any work done in it since.

The board reconnects by itself while Solace restarts in the new place.

Several projects on one board

One board can show several Gleam projects: those in one folder, the root. The root's own project, if the folder is a Gleam project, comes first, then any project in a folder below it. Choose Projects to add an already set up project back to the board, remove one, or create a new one: give a package name, and optionally a folder and whether it runs on Erlang or JavaScript, and Solace runs gleam new and sets the project up. Every project stays inside the root; a folder outside it, or reached through a link, is refused. The list is kept in the root's solace.toml.

Each project keeps its own tasks, settings, AGENTS.md and agents, and agents in different projects can work at the same time. An agent changes only its own project, but can read the others, for example to see how a project it depends on works. Reading never waits for another project's agent. A lane names its project's folder, counts its tasks, and has its own Contract view; select the folder name to fold the lane away. When every project uses the same columns they share one header row; otherwise each lane names its own. Notices start with the project's folder. A notice's Show task button opens its task on the tab that has the news (Questions for a question, Notes when the run left a note, else Runs) and scrolls it into view.

Tasks

A task is a piece of work you write for an agent: a title and a description. The description can refer to existing behavior, ask for changes, suggest something new, or just ask a question.

Tasks are created on the Strategy page with New task, and show on the board from then on. Select a task to see it: under its title are the model and effort to use, an editor, the actions you can take (with Add note), and tabs for its details, notes, questions, runs and changes, newest first. To change a task's title, description or order, use Edit on its Details tab. Descriptions, notes and instructions are markdown, styled as you write; images can be added once the task exists. A card shows ✓ once the task is approved. When an agent asks a question or a run ends, a notice appears in the corner of the board.

The editor takes markdown for notes, answers and instructions. Its buttons add headings, bold, code and code blocks, bulleted and numbered lists, quotes and links. The editor shows the markdown styled as you write: headings, bold, code, quotes and links look as they will, and images show in place. The marks that make them (#, **, backticks, >, a link's address) show only on the line you are editing. To add an image (PNG, JPEG, GIF or WebP, up to 5 MB), paste it, drop it on the editor or choose Image. Agents see the images in the notes they are given. Each note can be collapsed, and an agent's note names the run that wrote it.

Each column says what an agent may do there. In Planning, investigate starts an agent that looks into the task and reports back: an answer to a question, or a plan for the change. It changes nothing. If the task was only a question, complete it once you have the answer. Otherwise assign it, and the agent that does the work gets the report with the task's other notes. An agent changes the project only once the task is Assigned. A review agent, in Needs review or Assigned, looks at what the task changed and gives feedback.

The default columns

ColumnWhat it meansWhat you can do
BacklogWritten, not yet being plannedPlan it, or cancel it
PlanningYou're shaping the taskAsk an agent to investigate it, assign it to a model, complete it (when it only needed an answer), send it back, or cancel it
AssignedAn agent is working, or needs your answer or stopped (the card is marked Needs attention)Answer it, reassign it, start a new agent, ask for a review, or cancel it
Needs reviewThe agent says it's finishedApprove it, then complete it; ask for an agent review; reassign it for fixes; start over; or cancel it
Complete, CanceledFinished either wayNothing

A task with an agent on it says so on its card: Agent investigating, Agent working, Agent reviewing, Waiting for your answer or Agent paused.

If a review finds problems, enter any additional instructions in the editor and choose reassign. The task returns to Assigned and a work agent gets the review feedback and notes. Existing changes are kept, and any approval is cleared. You can select another model first. Wait for an active review to finish before reassigning. Start over instead undoes the task's changes before starting another agent.

You can pause any task that isn't finished, and resume it later. A paused agent stops at its next step and keeps what it knows.

A task can't be completed until you approve it. If you move an approved task anywhere else, for example by starting over, it loses the approval.

Cancel and Complete ask for confirmation. Cancel stops the task's agents and reverts its changes. Complete keeps the changes and closes the task, removing its undo records; the board cannot reopen or revert it afterwards. Dismissing either dialog leaves the task and your entered instructions unchanged.

You can change the columns and what's allowed in each in the project's solace.toml (see Settings below).

Questions and attention

Solace keeps the author's conversation through investigation, implementation and review fixes when compatible. Each review starts fresh. Changing models or losing a conversation automatically gives the next agent a handoff with feedback, changes and verification results. You do not need to manage sessions. Finishing agents get time to exit normally; author conversations are cleaned up when the task is completed or canceled, and reviewer conversations after their review.

When an agent needs a decision, it asks a question with a few options, and the task stays in Assigned, marked Needs attention. The agent waits, keeping everything it has learned so far. Pick an option or submit a written answer. Once every pending question is answered, the same agent automatically carries on. An investigating agent stays in Planning and continues the same way. If you paused the task, answers are saved and it stays paused until you choose resume. If you'd rather start fresh, new agent starts another one, which gets the task's notes and your answers.

An agent can't change the project's settings (solace.toml) itself. When a task needs one, for example a new command to build the app, the agent proposes the change as a question titled Change solace.toml, showing the lines it would remove (-) and add (+). Approve writes it; Reject, or a written answer, leaves the file alone and tells the agent why. If the file was changed after the agent proposed it, approving does nothing and the agent is told to propose again.

A task marked Needs attention is waiting on you. That happens when an agent asks a question, when an agent stops unexpectedly (it crashed, ran out of time, lost its connection, or its model became unavailable), or when Solace was restarted while an agent was working. The reason is shown on the task, together with the agent's last message when there is one. The run's activity shows everything that led up to it. The mark goes away when you next act on the task, except when an agent is waiting on your question or a working agent stopped: then it stays until that agent carries on, a new agent starts, or the task is stopped, canceled or completed. (Blocked is kept for tasks that will depend on other tasks.) Likewise, Agent finished, Report ready or Review ready marks a task whose agent has finished its work, investigation or review, until you next act on it. To continue, reassign it or start a new agent, and choose a different model if the first one isn't working.

Following an agent

Every run of an agent is listed under Runs on the task, newest first. Follow live shows what the agent is doing as it happens: its messages, its thinking, and each Solace command it runs. Open a command to see what it sent and what came back; a ✗ marks a command that failed. Show activity does the same for a run that has ended. It's a view only, so you can't interrupt or talk to the agent from it. Use a note, an answer or pause for that.

Undoing a task

Cancel and start over undo everything the task changed, bringing the code and files back to how they were before it started. Solace refuses to undo a task when that would affect another open task: if a later task changed the same code, or depends on something this task added. The refusal names the other task, so you can undo that one first or leave things as they are.

Solace doesn't keep a history beyond that. Use your own version control (such as git) for history.

Changes made outside Solace

Code is meant to change through tasks, but you can still edit files yourself, pull from git or switch branches. Solace never writes over a source file it didn't write last. It reads your edit in instead.

If an agent is working, the edit becomes part of that agent's task and shows in its review. If no agent is working, the edit goes to a task called Unexpected Changes, marked with a yellow hazard sign, in needs_review. Its note lists what changed and whether the code still compiles. Approve and complete it to keep the changes, or cancel it to put back the code Solace had. No agent starts work until it is completed or canceled, so agents never build on code nobody has looked at. You can also reassign it to have an agent fix it.

Code that came from Solace stays quiet: when you pull or switch to a branch whose code was approved in Solace, it is read in without a task. That works through .solace/approved, a list Solace keeps current; commit it with your code. Only Gleam files under src/ and test/ count. Other files you add, such as data or documents, never raise Unexpected Changes.

Models

You choose a model each time you assign a task or start a new agent. Solace runs the model through an agent program you already have installed and signed in to: the Codex CLI for OpenAI models, or Claude Code for Claude models. Solace doesn't store any credentials itself.

A list of current major models is built in. A model that can't be started right now is greyed out in the list, with the reason: the agent program isn't installed, it isn't signed in, or a key it needs isn't set.

Add your own models, or change the built-in ones, in ~/.config/solace/config.toml:

task_timeout = 3600            # seconds an agent may work; time spent waiting for you doesn't count

[[models]]                     # a model through the normal Codex sign-in
id = "codex-terra-high"
label = "Codex · Terra (high effort)"
agent = "codex"
model = "gpt-5.6-terra"
effort = "high"

[[models]]                     # any OpenAI-compatible endpoint, through Codex
id = "local-qwen"
label = "Qwen3 Coder (local)"
agent = "codex"
model = "qwen3-coder"
endpoint = { kind = "openai", base_url = "http://localhost:11434/v1", key_env = "LOCAL_LLM_KEY" }

[[models]]                     # any Claude-compatible endpoint, through Claude Code
id = "proxy-sonnet"
label = "Sonnet via our proxy"
agent = "claude"
model = "claude-sonnet-5-5"
endpoint = { kind = "anthropic", base_url = "https://llm-proxy.example.com", key_env = "PROXY_KEY" }
  • effort is the model's default. The board lets you pick another effort for each action: low, medium, high or xhigh for Codex, and also max for Claude Code. Changing it starts the agent's conversation afresh, with a handoff.
  • An entry with the same id as a built-in model replaces it. Add presets = false at the top to hide the built-in list.
  • An endpoint's key is never written in the file. key_env names an environment variable that holds it, and Solace reads that variable when it starts the agent. Leave key_env out for an endpoint that needs no key.
  • Codex talks to OpenAI-compatible endpoints through the Responses API, so the endpoint has to support it.

Contract view

When a task changes the project, its Changes tab shows a review summary and a link to the contract view. The graph reports entry points, logic, derived effects, tests and project files. Effects are inferred from known calls and external declarations; they are not guarantees. Review compares the current project with its state before the task, and you can run the task's tests from the view API. Open Contracts to explore the drawing sheet. Search by name or summary, select a box to expand its connections and read its detail, and read its detail. The panel on the right has tabs: Review (for a task), Details (the box you opened) and Files, which lists the project’s files grouped as watched, protected and unwatched; click one to read it in place of the drawing. Close folds the panel to its tabs. The house button returns to the default view; disconnected entries fill rows. The header names the project and the task under review. A note says when no effects were found. On a phone, open Legend for kind colors and connector meanings. Drag the sheet to pan (dragging never selects), or use the zoom buttons. The selected box has a thick border. A box shows +N for connections not yet drawn, or − when expanded; arrows point from a function to what it calls, uses or tests (hover a connector to read it). Drag the panel’s left edge to resize it. Keys: arrows or WASD move between boxes, Shift with them pans, Ctrl+Up and Ctrl+Down zoom, Space expands a box, C collapses it, Shift+Space expands everything, Shift+C collapses everything (the two arrow buttons by the zoom buttons do the same) and Enter opens a box. A box with no connections has nothing to expand. A task’s review link marks additions, changes and removals and runs its tests when needed. Show source gives the source text; for a function the task changed, it shows what changed. Run forms and replay come later.

Each file in the graph is labeled with how Solace treats it: watched, protected or unwatched, as described below.

What agents can touch

Solace puts every file in the project into one category, named for what Solace does with it:

CategoryFilesWhat agents can do
GraphGleam files in src/ and test/, held as symbolsRead and change code through Solace, one entry at a time
WatchedEvery other text file up to the size limit, including gleam.tomlRead and write, checked by any validator you declare; undoing a task restores them
Protectedsolace.toml and AGENTS.mdRead; a change they want waits for your approval
Unwatched.git/, build output, anything .gitignore ignores, paths you list under unwatched, binary or oversized filesRead and write
Internal.solace/, Solace's own files, and any other Solace project inside this oneNothing

File writes are limited to 256 KiB unless you change watch_limit, and require a current read or an exact replacement. Watched and unwatched file contents never appear in symbol searches.

Settings

solace.toml in the project's root holds the project's settings. solace create creates a starter file if it is missing and preserves an existing one. Only you edit it; agents can read it, and an agent that needs a change has to ask you. Every part is optional.

watch_limit = 262144                       # bytes
unwatched   = ["priv/generated/"]

[validators]                               # must pass before a file change is kept
"priv/**/*.html" = ["tidy", "-q", "-e", "{file}"]

[commands]                                 # extra commands agents may run
smoke = { run = ["gleam", "run", "-m", "smoke"], timeout = 60 }

Agents can always check, test, format and build the project. Under [commands] you add anything else they may run. Commands run without a shell, so agents can't chain or alter them, and they can pass extra arguments only to a command that sets args = true.

A [board] section replaces the default columns and actions. It's described in the Solace repository's board specification.

Limits for now

  • Projects must be written in Gleam.
  • One agent works on a project at a time. While one is working, assigning another task in that project is refused.
  • A task belongs to one project. Its agent can read the other projects but can't change them, even one its project depends on.
  • Tasks that are still open aren't kept apart: a later task sees the unapproved changes of earlier ones.
  • The board runs on your machine only, for one person, with no sign-in.
