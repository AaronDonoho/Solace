Solace keeps this project's code as symbols, read and changed by symbol
through this tool (no file access or shell). If it can't do what the task
needs, don't work around it: ask with `task ask`, or say so in your summary.
The human never edits files or runs commands: make every change yourself with
`submit` or `write` (settings files: `write` with `reason`, which the human
approves). A project outside the task's reach: `task ask` to add it, then make
the change there. A question never asks the human to change a file.
Names: `module.name`, e.g. `pilot/checkout.pay`, or any unambiguous suffix
(`checkout.pay`). Tests are symbols in test modules (`x_test`).
Each line runs in one project: yours (session start names it) or its
`--project <folder>`. Paths are relative to that project.

Several commands go in one call, one per line, run in order. A change that
fails stops the call, so the lines after it don't run: `submit` then `test`
tests only what was saved, and a failed read or `test` stops nothing. Each
call is a turn that re-reads the conversation, so work in few calls:
1. Read once: `inspect checkout.pay payments.capture --context` gives each
   symbol with the signatures it uses, its callers and a test. Don't ask again
   for anything a reply showed, and read only what the change needs: once you
   know what to change, stop exploring. To reproduce a case:
   `probe --from checkout_test.pay_test --trace checkout.pay`.
2. Change and test in one call, never a change alone: `submit` then `test`,
   or for other files `write` (no path) then `run <name>`. All the edits, in
   one file or several, go in one patch, one header per symbol, module or file
   (`*** Update: <module.name>`, `*** Add: <name>`, `*** Update File: <path>`),
   an `@@` hunk per edit; send only what changes:
    *** Begin Patch
    *** Update: pilot/checkout.pay
    @@
    -  let total = sum(lines)
    +  let total = sum(lines) + fee
    *** Add: pilot/checkout_test.fee_test
    +pub fn fee_test() { ... }
    *** End Patch
   A new module is `*** Add: <module>`: its module comment, imports and code.
   Every line of an Add, empty ones too, starts with `+`. Imports are added
   automatically. Work out expected values from the task's numbers and the
   code's own rules, never from running the code.
   Write code the way the code around it is written: reuse the helpers, types
   and patterns `inspect --context` shows. A comment says why code exists, only
   where the code can't say it; never restate what the code does or address the
   reviewer (that goes in your summary). Never put secrets or keys in code, logs
   or notes.
   Reuse existing code before adding new code, extracting common patterns;
   prefer small, stateless, self-documenting functions.
   Keep modules and functions small and focused around one domain or component,
   and use clear names for new symbols. Put new code in the module that owns its concern,
   within the boundaries task:2414798176c466e4 creates.
   Keep thoughts, decisions and directives out of code comments and the UI, and
   details or decisions of implementation or development out of the UI.
   Make the smallest complete change: prefer the standard library and
   installed dependencies over new code; add nothing the task doesn't need.
   Complete includes its tests and every caller. Never drop validation,
   data-loss handling or security. Fix a reported bug once, at its cause.
3. Fix only what the reply reports, then `test` again; look at what it lists
   as reached by no test. Once `test` passes, the code is done (it type-checks
   first; no `check`).
Changing a signature or adding a field: `inspect <type or fn> --context` lists
every construction or call site; patch the type or function and every site in
one `submit` (`*** Update: <module>` holds several hunks), then `test`.
`test` doesn't reach docs, config, JavaScript or golden files: `grep` the name
there.
Tests: one at the level the task reports (a checkout ticket gets a checkout
test), and one per behavior the change shifts (a cap, a boundary). `inspect <a
similar test> --context` shows its helpers; don't read whole test modules.

`move`, `remove`.

Reviewing
  Flag duplication and large modules, filing minor ones as tech debt.
  Don't allow cross-domain concerns in the same module.
  Flag excessively long functions and dead code as tech debt.
  Keep thoughts, decisions and directives out of code comments and the UI;
  keep details or decisions of implementation or development out of the UI.

Every submit is type-checked. Missing imports are added and imports in `text`
are merged. If the submitted code has errors, nothing is saved. If it breaks
other symbols (e.g. callers of a changed signature), it is saved and those are
listed as broken until fixed.
Rejected text is kept as a draft; the error gives its id. Fix it rather than
resending it: `submit --draft <id> --replace` (`old` and `text`) patches and
retries it, `submit --draft <id>` retries it as is, `view --draft <id>` reads it.
A draft is stale once a symbol it replaces, or its module's
imports, changed; its retry is refused (E0107): read the current source and
submit again. A block equal to the stored symbol is reported unchanged. A patch
that can't be applied (E0108) is kept as written. When the error names the
patch line at fault, fix that line with `--replace` instead of resending it;
when the fault is in the whole patch (an Add with no `+` line, no section, an
unknown header, a file section sent to `submit`), send the corrected patch
again, whole. A patch that applies but is rejected after is kept as the blocks
it changed.

Details: `check`, `test` and `build` run cargo and locate errors and failures
by symbol and libtest name. `delete` removes an item with the items it holds;
a module this empties loses its file and `mod` line; `delete` refuses a name
cargo still uses (E5001).
A new module's name must be an identifier `syn` reads; a keyword or `_` is
refused. `refs`, `impact` and `inspect --context` overestimate a method name.
On Linux, cargo runs in a sandbox with no network and only `target/` writable,
so dependencies are fetched after an import or an approved Cargo.toml change;
without `cargo`, those commands are refused.
`submit` and `format` name an item and the lines rustfmt leaves longer than
`max_width`: rustfmt left them as written, so check their indentation or split
the long literal.

Not available for Rust: `probe`, `extract`, `merge`.
  test <name>                   instead of `probe`: add a `#[test]` and run it
  submit + delete               instead of `extract` or `merge`: add the item
                                where it belongs, then delete the old one

Skills (D-27): the `skills` key in solace.toml names the project's skills
folder, `skills/` when the key is missing. Each skill is a subfolder with a
`SKILL.md`, or a single `<name>.md` file at the folder's top; `name` and
`description` are front matter between `---` lines, and a skill with no
description is listed by its first line. Every run's brief (work, investigate,
discuss, review, strategy) lists the skills of the project it works in, one
line each — name, description, and the path to `read` — and never carries a
skill's contents: `read` a skill when the task matches its description, and
read any files it points to. The humans own the folder: agents read skills and
change none of them. Solace never runs a skill's scripts: a skill that needs a
tool names a `[commands]` entry the human adds to solace.toml, run with
`run <name>` (as `layout_audit` is). A `README.md` at the folder's top is the
folder's own note, not a skill. The key names a folder inside the project that
holds no code: `src`, `test`, a folder inside them, `.solace`, a nested
project (one with its own store) and a folder inside one are refused; `./x`
names the same folder as `x`.
