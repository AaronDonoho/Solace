Solace: this project's code lives in a store of symbols. You read and change it
by symbol through this tool; you cannot open files or run a shell. If it can't
do what the task needs, don't work around it: ask with `task ask`, or say so in
your summary.
Names: `module.name`, e.g. `pilot/checkout.pay`, or any unambiguous suffix
(`checkout.pay`). Tests are symbols in test modules (`checkout_test`).

Several commands go in one call, one per line, run in order. Each call is a
turn that re-reads the conversation, so work in few calls:
1. Read once: `inspect checkout.pay payments.capture --context` gives each
   symbol with the signatures it uses, its callers and a test. Don't ask again
   for anything a reply showed. To reproduce a reported case:
   `probe --from checkout_test.pay_test --trace checkout.pay`.
2. Change and test in one call: `command` is `submit`, then `test` on the next
   line. To edit code, `text` is a patch as `apply_patch` takes, naming a
   symbol or module instead of a file; send only what changes:
      *** Begin Patch
      *** Update: pilot/checkout.pay
      @@
      -  let total = sum(lines)
      +  let total = sum(lines) + fee
      *** Add: pilot/checkout_test.fee_test
      +pub fn fee_test() { ... }
      *** End Patch
   Imports are added automatically. Work out expected values from the task's
   numbers and the rules the code documents, never from running the code.
3. Fix only what the reply reports, again with `test` after. The reply lists
   what else the change reaches that no test checks; look at those.
4. Once `test` passes, the code is done (it type-checks first; no `check`).
Changing a signature or adding a field: `inspect <type or fn> --context` lists
every construction or call site; patch the type or function and every site in
one `submit` (`*** Update: <module>` holds several symbols' hunks), then `test`.
Tests: one at the level the task reports (a checkout ticket gets a checkout
test), and one per behavior the change shifts (a cap, a boundary). `inspect <a
similar test> --context` shows its helpers; don't read whole test modules.

Commands (`help` gives every option, `help <command>` one command's):
  inspect <name>... --context   symbols with what they use, callers and tests
  view <name|module>...         source, or a module's outline
  refs <name>...                what uses each symbol
  impact [name...]              what a change reaches, with its tests
  find <text>                   search all code
  grep <text>                   search other files and settings
  submit                        save a patch or blocks from `text`, type-checked
  delete <name>...              remove unused symbols
  extract <name>... --to <mod>  move symbols to another module
  test [<name>... | --all]      run the tests a change can affect
  check [--warnings]            type-check everything
  probe                         run throwaway code from `text`
  drafts                        rejected submits, kept to fix and retry
  files [dir]...                trees of files, each with its tier
  read <path>...                read files
  write [path]                  change a file; no path: several, by patch
  move <from> <to>              move a file
  work add | list | done        work records, kept between sessions
Files by tier: src/ and test/ *.gleam are symbols (`submit`, never `write`);
solace.toml, AGENTS.md, .gitignore: `write` with `reason`, the human approves;
.solace/ and nested projects: their own commands; any other file, ignored
or not: `read`, `write`, `move`, `remove` (not gleam.toml). `help` has the table.

Commands in full
Reading
  inspect <name>... --context   symbols, the signatures of what they use, their
                                callers, and the tests that use them (the
                                smallest in full)
  view <name>...                symbols' source
  view <module>...              outlines: signatures and doc lines
  view <module> --bodies        whole module; only for one you will rewrite
  view | inspect <dependency>   a dependency's module (`lustre/component`): its
                                public signatures; `<module>.<name>`: one with
                                its docs. Read from build/packages, never stored
  refs <name>...                everything that uses each named symbol, in the
                                order named
  refs <module>.<Type>.<field>  code that reads a record field
  impact [name...]              what a change reaches: callers and readers of the
                                fields it changes, nearest first, with their
                                tests (no name: what changed since tests last
                                passed, or in this task)
  find <text>                   case-insensitive search of all code
  grep <text>                   case-insensitive search of watched files and
                                settings (not unwatched files); lines shown
                                with numbers for `read --lines`. Literal text,
                                one term per command: no options, regex or
                                file arguments
  session start [--task]        this overview again (--task: for the task in `text`)
  session start [--scope <module>...]
                                every symbol, and open work records with context
  ... --project <folder>        view, inspect, refs, find, grep, files and read in
                                another project under the same Solace root
                                (session start lists them); any command in
                                another project the task covers (its brief
                                lists them), so it changes that project too
Replies have a size limit: a signature is printed once per reply, and a reply
that would be larger says what it left out and the command that shows it.

Changing (the new code is in `text`)
  submit                        several symbols, checked together: a block each,
                                headed `// ── <module>.<name> ──` as view prints
                                them; a new name adds the symbol, and its module
                                if needed
  submit (a patch)              edit existing code: `*** Begin Patch`, then per
                                symbol or module `*** Update: <name>` with `@@`
                                hunks (` ` context, `-` removed, `+` added),
                                applied in order like `apply_patch`; `*** Add:
                                <module>.<name>` with `+` lines adds a symbol.
                                Checked together; a hunk that doesn't match
                                changes nothing (E0108). Other files change
                                with `write`, not here
  submit <name>                 replace one symbol (may rename it)
  submit <name> --replace [--all]
                                one exact change: `old` (must occur once, or
                                every occurrence with --all) becomes `text`;
                                the whole symbol is checked
  submit --new <module>         add symbols, or create the module whole (module
                                comment, imports, symbols; under test/ if the
                                name ends in `_test`)
  submit <module>               replace a whole module; it must keep every symbol
  submit --imports <module>     replace a module's imports and module comment
  delete <name>...              removes each named symbol, in the order named; a
                                symbol used outside the list stops the whole
                                list, so nothing is deleted
  extract <name>... --to <module>
                                move symbols to another module of the project,
                                keeping identity and revision. Private helpers
                                only they use, tests that reach only them, and
                                every reference and import come along; the
                                result is type-checked or nothing changes.
                                `--to solace_task.gleam` is read as solace_task;
                                tests go only to a *_test module. Extract a
                                cohesive set in one call; the refusal (E5002,
                                a module cycle) lists everything to add:
                                  extract board.Task --to solace_task
                                  E5002 moved code uses 1 symbol that stays: lane_order (by Task.sort)
                                  extract board.Task board.lane_order --to solace_task
Every submit is type-checked. Missing imports are added and imports in `text`
are merged. If the submitted code has errors, nothing is saved. If it breaks
other symbols (e.g. callers of a changed signature), it is saved and those are
listed as broken until fixed.
Rejected text is kept as a draft; the error gives its id. Fix it rather than
resending it: `submit --draft <id> --replace` (`old` and `text`) patches and
retries it, `submit --draft <id>` retries it as is, `view --draft <id>` reads it,
`drafts` lists them. A draft is stale once a symbol it replaces, or its module's
imports, changed; its retry is refused (E0107): read the current source and
submit again. A block equal to the stored symbol is reported unchanged. A patch
that can't be applied (E0108, with the patch line at fault) is kept as written,
so fix that line with `--replace` instead of resending it; a patch that applies
but is rejected after is kept as the blocks it changed.

Checking
  test                          run the tests that can see a change since they
                                last passed (and any that failed); shows
                                failures only
  test <name>...                run the tests that reach these symbols
  test --all                    run every test
  check [--warnings]            type-check everything; lists broken symbols
  probe                         run throwaway code (`text`) and show its output;
                                nothing is saved. Statements become `main`'s
                                body, or give a module with `pub fn main()`;
                                `echo value` prints a value, and a single
                                expression is printed
  probe --from <fn>             start from a test's (or any function without
                                arguments) imports and body; `text` adds
                                statements that can use its variables
  probe --trace <fn>...         also show each call to these functions, with
                                its arguments and result (combines with --from)

Files: every file is in one tier, by the first rule that matches, and the tier
is what says what you may do with the file. `files` prints each file's tier. A
file you can't change with `write` isn't a file you can't change: graph files
change with `submit`, protected ones with `write` and the human's approval.
  graph     src/ and test/ *.gleam, the code in the store: `read` and `write`
            are refused (E6001); change it with `submit` and `delete`
  watched   every other text file within watch_limit, gleam.toml included (new
            dependencies are fetched by check, test and build): `read`, `write`,
            `remove` and `move` work; searched by `grep`; a task's changes to
            them are recorded, and undone if the task is canceled
  protected solace.toml, AGENTS.md (the project's instructions for agents, shown
            at session start) and every .gitignore: the human owns them. In a
            work run, `write` one alone, with the exact new text and the why in
            `reason`; it waits for the human's approval (no `task note` beside
            it; don't ask in prose)
  unwatched .git, build and dependency output, .gitignore'd files, paths in the
            `unwatched` list, node_modules, binary files and files over
            watch_limit: `read`, `write`, `remove` and `move` work; listed by
            `files` (folders as one line with a count), not searched by `grep`
  internal  .solace/ and projects nested in this one: no reading, writing or
            searching; work in them through their own commands
  files [dir]...                tree with each file's tier; no path: the project
  read <path>... [--lines 3,7,10..12 | --tail n]
                                each path in order, headed by its path when
                                several; paths past the size limit are named
                                in a `Next: read` line. --lines takes lines and
                                ranges, shown in file order; a --lines or --tail
                                range takes one path
  write <path> [--all]          one file: whole text, or with `old`, just `old`
                                -> `text`; a settings file takes `reason` too
  write                         several files at once: `text` is a patch, as
                                submit takes, with a section per file:
                                  *** Begin Patch
                                  *** Update File: docs/guide.md
                                  @@ ## Usage
                                  -old line
                                  +new line
                                  *** Add File: docs/new.md
                                  +every line of the new file
                                  *** Delete File: docs/old.md
                                  *** End Patch
                                Update hunks match as submit's do, with no read
                                first; added lines with no `@@` go at the end.
                                Whole or nothing: any refused section (graph or
                                protected file, unmatched hunk, failed
                                validator) writes none, and each is named
  remove <path>...              files, whole or nothing: any refused path
                                removes none and is named
  move <from> <to> [--to-project <folder>]
                                move a file or folder, whole or not at all, never
                                onto anything that exists; graph, protected and
                                internal files stay put. --to-project: another
                                project of this task. A repeated move changes
                                nothing
Project: build | format | run <name> [args...] (commands declared in solace.toml)
Work records, kept between sessions: work add (`text`) | work list | work done <id>

Task runs (the note, summary or question in `text`). Reviews and investigations
are read-only: submit, delete, extract, write, remove, move and format are refused, and so is
run, except in a review for commands marked `allowed_in_reviews = true`.
  task diff [name...]           what this task changed, against its state before;
                                `impact` with no names is the same
  task note                     add a note; completes a review run
  task ask                      a question, with 2–4 `options`; waits for the
                                human's answer
  task done                     finish: a work run's summary goes to human
                                review; an investigation's report stays on the task
  In notes, cite code by name (`board.rs::within`, `checkout.pay`), not by
  `file:line`: line numbers move.

Strategy runs (planning with the human on the Strategy page): read only; any
command not listed here is refused.
  strategy list [--archived]    one line per task, feature and milestone, then
                                the vision; --archived adds archived tasks
  strategy show <task|feature|milestone> <id>...
                                one id: the ids the record links to, then the
                                record (a task in brief, its notes, questions and
                                runs one line each; a feature or milestone in
                                full); several ids: each record in one reply
  strategy show note <task> <notes> [--from <n>]
                                a task's notes in full, each with its number:
                                3,7,10..12, or all; a reply stops at a whole
                                note, and a `Next:` line names the rest. A note
                                too long for one reply comes in parts: its
                                `Next:` line ends in --from n, its next part
  strategy show run <task> <run> [<steps>|all] [--from <n>]
                                a task's run log: one line per step; with
                                steps (3,7,10..12) or all, those steps in full,
                                stopping at a whole step as notes do
  strategy note                 reply to the human, the reply in `text`; waits
                                for their next message. Text outside it shows
                                only in the run's live transcript on the page
  strategy task|feature|milestone [<id>]
                                propose creating one (no id) or editing one: the
                                request's fields as a JSON object in `text`;
                                waits for Approve or Reject. Alone in its call.
                                task: title, body, feature, milestone,
                                dependsOn (task ids), and scope (folders) only
                                when creating. feature: title, body,
                                milestone, state. milestone: title, body,
                                targetDate, state. Any of them: rank only when
                                editing. state: proposed|planned|active|
                                complete|canceled. Other fields are refused.
                                A title is the work in 3-7 words (`extract: JS FFI
                                 files`); details go in body. The human sees
                                 body as Markdown, the rest as
                                text
  strategy vision               propose a new vision, its text in `text`; waits
                                the same way
  view | inspect | refs | find  read code, as under Reading
  grep <text>                   search watched files and settings: literal text,
                                already case-insensitive, one term per command
  files [dir]...                tree with each file's tier
  read <path>... [--lines 3,7,10..12 | --tail n]
                                each path in order; a --lines or --tail range
                                takes one path
  ... --project <folder>        read in a project below the root; in a folder of
                                projects, every read needs it
  In notes and proposals, cite code by name (`board.rs::within`), not by
  `file:line`: line numbers move.

Host commands (humans only, refused in a run)
  create <name> [--javascript] [--yes]
                                create a new Gleam project below this folder;
                                asks for confirmation unless --yes
  migrate [--project DIR]... [--smoke CMD]... [--confirm-paths] [--yes]
                                copy this folder to ../solace-migration, set
                                up the chosen projects there and check them;
                                stops first, until --confirm-paths, if anything
                                in the copy could change this folder
  migrate --report              what Solace checked
  migrate --recheck             build, test and check the copy again
  migrate --adopt [--yes]       switch to the copy; this folder moves to
                                <name>.pre-solace
  migrate --abandon [--yes]     delete the copy
  migrate --undo [--yes]        switch back to <name>.pre-solace
  serve [--port N]              local task board (default 3030); in a workspace
                                folder, every project's
  agent-config codex|claude <dir>
                                isolated settings and launch.json for a runner
From a shell, `text` is stdin, `old` is `--old <text>` and each option is
`--option <label>`.
